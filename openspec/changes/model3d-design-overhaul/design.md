# Design

## Context

The explorer's chrome is styled entirely through CSS custom properties and plain classes in `leoiot-3d/explorer/src/ui/styles.css` (`--bg`, `--surface`, `--border`, `--text`, `--muted`, `--accent`, `--warn`), consumed by `controls.ts`, `panel.ts`, `loading.ts`, `navigation.ts` and `routeLegend.ts`. There is no component framework or build-time theming layer — elements are built with plain DOM calls and styled by class name. See proposal.md - Why for the motivation.

## Goals / Non-Goals

**Goals:**
- Make the chrome bold and high-contrast (stronger borders/elevation, heavier type weight for labels and buttons, more deliberate use of the existing accent colour) while keeping the same `:root` custom-property names, so every consumer keeps working unchanged.
- Consolidate the primary always-visible controls (floor/view switching, heatmap toggles, room search) — previously three separate floating panels — into one grouped bottom dock, for desktop-browser use primarily.
- Keep the purely-visual part of the change (tokens, colours, type) CSS-only; the dock restructuring necessarily touches markup (`controls.ts`, `navigation.ts`, `main.ts`), but only to regroup existing elements, not to change what they do.

**Non-Goals:**
- Introducing a design system, CSS framework or build step (Tailwind, CSS-in-JS). The project has none today and this change does not need one for a single stylesheet.
- Changing the `--bg`, `--accent`, `--warn` values or the heatmap/legend colour constants in `core/colours.ts` and `core/heatmap.ts` — those stay as specified by `model3d/room-heatmap` and `model3d/room-navigation` (proposal.md - What Changes).
- Restyling the 3D canvas, camera or model materials.
- Optimizing the dock for touch/kiosk or mobile layouts: on narrow viewports the dock stays a single compact row and scrolls horizontally rather than wrapping or stacking, which is functional but not a first-class mobile design (desktop browser is the stated primary context).
- Moving the room info panel or the route legend into the dock: they are contextual results (shown only when a room is selected or a route is active), not primary controls, so they keep their existing floating positions.

## Decisions

- **Keep the existing custom-property names, change their values and add new ones for the bold treatment** (e.g. a heavier border width/colour token, a bolder font-weight token) rather than renaming variables. Alternative considered: introduce a new token set and migrate call sites — rejected, it touches every UI file for no behavioural gain and raises merge-conflict risk against the other in-flight `model3d-*` changes editing the same files.
- **Style purely through `styles.css` class rules**, not inline styles in the `.ts` files, so the visual language stays in one place.
- **Leave `core/colours.ts` and `core/heatmap.ts` untouched** so the semantic heatmap/legend colours are provably unchanged (proposal.md - Capabilities / `model3d/visual-design`).
- **One `.dock` wrapper, assembled in `main.ts`, holding three dock-group elements owned by their existing classes**: `Controls` now exposes `resetElement` (View: just Reset View) and `overlaysElement` (Overlays: heatmap toggles) instead of one `.bar`; `Navigation.element` becomes the Search dock-group (toggle + popover), with `nextFloorElement` exposed separately since it is positioned above the dock, not inside it. Alternative considered: a single new `Dock` class owning all of this directly — rejected, it would merge `Controls`' view/heatmap state and `Navigation`'s search/route state into one class for a purely presentational grouping; `main.ts` composing existing components' elements is a smaller, more reversible change.
- **The search popover (`.nav-panel`) opens upward as a `position: fixed` overlay**, and `Navigation.closeOnRouteStarted()` closes it once `App.navigate()` actually starts a route (called from `app.ts`, not on a rejected destination, so the error message in the popover stays visible per `model3d/room-navigation` "Invalid destination does not start navigation"). This keeps the popover from overlapping the repositioned "Next floor" control, which now sits directly above the dock instead of alone at the bottom-centre.
- **`.dock` is left-aligned with `left: 16px`, not centred, and still without `transform`.** A `transform` on an ancestor becomes the containing block for any `position: fixed` descendant (here, the search popover), which silently re-anchors and clips it instead of letting it escape to the viewport — found by actually opening the popover in a browser, not by static review, when the dock was still centred this way. Left-aligning it keeps that constraint; it also puts the dock on the same edge as the floor stepper, per the request to move "the rest of the menu" to the left once floor switching became its own control.
- **`Navigation.positionPanel()` reads the Search toggle's own `getBoundingClientRect()` and sets `.nav-panel`'s `left` from it (on open, and again on window `resize`) instead of a fixed `left: 50%`.** The dock is now left-aligned and variable-width (its content changes which groups it holds), so a screen-centred popover would drift away from the toggle that opened it; anchoring to the toggle itself stays correct regardless of dock width or position.
- **Floor switching is its own `FloorStepper` component (`floorStepper.ts`), not part of `Controls` or the dock.** The request was specifically for floor switching to move out of any dock/panel, with Gym handled the same way, while "the rest of the menu" (view reset, overlays, search) moved left as a separate unit — two different kinds of control (relative step vs. absolute choice) now have two different widgets, rather than forcing both into one dock group.
- **`FloorStepper` exposes three independent elements (`upElement`, `downElement`, `gymElement`), each its own bare `<button>` — no wrapping panel, no label.** First built as one boxed stepper (background, border, a floor-name label between the arrows), then corrected after the request was clarified: "just an arrow on the bottom, and an arrow on the top, not in this kind of menu" — the up arrow sits alone near the top of the screen, the down arrow alone near the bottom, Gym alone on the right, each styled as a plain `.button` with no container. The floor-name label was dropped along with the panel, since it only existed to live inside that panel; `strings.views.full` (added for it) was removed as now-unused.
- **`App.step(direction)` is the one place that computes the next floor from the current view**, extracted from what was only the arrow-key handler (`handleKey`) so the floor stepper's buttons and the keyboard do the exact same move through the exact same code, not two copies of the same bounds logic (`FLOOR_ORDER`, the `'full'` → index `-1` convention, no-op past either end or in the gym).
- **The selected-room watermark is plain 2D DOM text behind the canvas, sized in `vh`, not a 3D object in the scene.** "Nearly the height of the screen" is a screen-space size, not a world-space one, and a 3D label would scale with camera distance/zoom instead of staying consistently huge; a fixed, centred `<div>` sized in viewport units is simpler and matches the request directly. For it to read as *behind* the model rather than just behind the canvas element, `Viewer`'s renderer is now created with `alpha: true` and `setClearColor(0x000000, 0)` instead of an opaque `scene.background`, so the canvas is transparent wherever the scene draws no geometry (the "sky") and only opaque where the building itself draws — the watermark shows through the sky and is occluded by the building, the same depth relationship a 3D object would have, without the scaling problem.
- **The watermark's colour (`--watermark`) is a shade barely lighter than `--bg`, not the selection-highlight yellow used first.** A near-background tone reads as a bold embossed mark at this size without competing with the room's own yellow highlight on the model, the heatmap colours, or the chrome; "big and bold" here comes from scale and weight, not from a loud colour.
- **`RoomWatermark.show()`/`hide()` toggle a `--visible` class (opacity 0 → 1) instead of the `hidden` attribute, with a `transition: opacity` on the element.** `display: none` (what `hidden` produces) can't be transitioned — the element must stay in normal flow, at `opacity: 0`, for the fade to animate; `pointer-events: none` (already set) keeps it from intercepting clicks either way.
- **`font-size: min(100vh, 54vw)`, plus a same-colour `-webkit-text-stroke`, calibrated against the actual rendered glyph box, not the `font-size` value itself.** `font-weight` tops out at 900 — a stroke is the only further way to read as bolder. Font-size was tried as a plain `vh` value first and measured with a browser automation tool (a `Range` bounding rect around the text, since font metrics make the glyph ink a different size than the `font-size` box): an uncapped value pushed a short room id off both horizontal edges of the screen, illegible, before this `min(vh, vw)` form was derived from that same measurement.
- **Real room ids are not all short.** `leoiot-3d/explorer/src/nav/room-positions.generated.ts` has ids up to 7 characters (`UBiolab`, `U74.1`, `134_1`), not just 3-digit numbers — no fixed CSS formula fits every length, so `RoomWatermark.refit()` measures the actually-selected id's rendered width at runtime and scales `font-size` down (via an inline style override, reset before each measurement) only when it would overflow ~94% of the viewport width. This runs from `show()` and on window `resize`.
- **`refit()` measures via a `Range` around the text, not `element.scrollWidth`.** Verified with a browser automation tool: comparing the two at two different font sizes for the same long string showed `scrollWidth` under-reporting a `justify-content: center` element's overflow (it did not scale linearly with font-size), while the `Range` measurement did. Using `scrollWidth` would have made the single proportional scaling step in `refit()` undershoot, leaving the id still too wide.
- **`-webkit-text-stroke` is `em`, not `vh`.** A fixed-width (`vh`) stroke doesn't shrink proportionally when `refit()` scales the font down, which would also have broken the proportional-scaling assumption for a badly-overflowing id; `em` keeps the stroke proportional to the glyphs at any size.

## Risks / Trade-offs

- [Merge conflicts with `model3d-building-explorer`, `model3d-room-navigation`, `model3d-route-wayfinding` and `model3d-floor-arrow-keys`, which touch the same `ui/` files] → The dock restructuring is an additional, separate commit on top of the earlier pure-CSS restyle, so a conflict there is easier to isolate; coordinate merge order with the other changes' authors.
- [A bolder, high-contrast chrome could reduce legibility of the heatmap/legend colours it sits next to] → Keep chrome surfaces and the 3D view visually separated (panel backgrounds, borders) so chrome contrast changes don't bleed into how heatmap/legend colours read against the model.
- [A CSS `position: fixed` + transformed-ancestor bug like the one above is easy to reintroduce silently] → Verified by actually opening the popover with a browser automation tool after the change, not just by `tsc`/unit tests (which don't touch the UI layer at all); any future change to `.dock`'s positioning should be re-verified the same way.
- [Making the canvas transparent is a renderer-level change that could, in principle, affect how the model itself is composited (e.g. antialiased edges blending against a different background)] → Visually verified with a browser automation tool after the change: the building's appearance (materials, edges, shadows) is unchanged, since `--bg` is painted at the page level behind the canvas and matches the previous opaque `scene.background` colour exactly where no watermark is shown.
- [A measurement-based fit can still be wrong if the measurement itself is wrong, as `scrollWidth` was here] → Cross-checked `scrollWidth` against an independent `Range`-based measurement with a browser automation tool before trusting either; `body`/`#app`'s pre-existing `overflow: hidden` remains a backstop (clips rather than breaks layout) for any id `refit()`'s margin still underestimates.
- [Pre-existing bug, found while testing the new Gym button: `.button:hover:not(:disabled)` (specificity 0,3,0) beat `.button[aria-pressed='true']` (0,2,0), so hovering a selected/pressed button — Gym, a heatmap toggle — silently dropped its accent fill back to the plain hover tint] → Confirmed with a browser automation tool (`getComputedStyle` on a pressed-and-hovered button showed the hover background, not the accent one) before fixing it, rather than assumed from a screenshot; fixed by excluding `[aria-pressed='true']` from the generic hover rule and adding a dedicated, brighter hover state for the pressed one, so this applies to every button using these two rules together, not just the new one that surfaced it.
- [Gym was first placed at `right: 16px; top: 50%` — the exact same anchor as `.route-legend` — so an active route's legend fully covered Gym, not just overlapped it at the edges] → Found by measuring both elements' bounding rects with a browser automation tool during an active route, not by eye (the legend's opaque background hid Gym completely in a screenshot, which looked merely like "Gym isn't shown" rather than an obvious overlap bug). Moved Gym to `bottom: 16px` instead of vertically centred; re-verified against this building's actual worst-case route (to a floor-2 room, crossing 3 floors, the longest legend the real room data produces) with the same technique, confirming a 250px+ gap rather than assuming the fix worked.
